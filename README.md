# arXiv Research Explorer

A multimodal hybrid-search research assistant over a continuously growing corpus of arXiv papers (currently tracking `cs.AI`). It combines structured filtering (category, date) with semantic search over full paper text *and* embedded figures, then answers natural-language questions with citations back to the exact paper and section they came from — routing to a vision-capable model when a relevant figure is available.

**Live app:** [arxiv-research-explorer.vercel.app](https://arxiv-research-explorer.vercel.app)

## Why this exists

Uploading a single PDF to a chat interface and asking questions about it is something general-purpose AI assistants already do natively, it doesn't demonstrate anything a retrieval system does that a plain chat window can't. This project is built to actually require the parts of RAG that matter in practice:

- A corpus that grows on its own from a live source, not from whatever one file happens to be on hand
- Structured metadata (category, publication date) combined with semantic similarity in a single hybrid query, not similarity search alone
- Full paper text *and* figures, not just abstracts, so answers can draw on methodology, results, and visual data, not only the summary
- A reranking step that re-scores retrieved candidates for precision, rather than trusting raw similarity scores
- An unattended ingestion pipeline that scrapes, cleans, indexes, and captions new papers and their figures on a schedule

## Features

- **Hybrid search:** natural language queries combined with category and date-range filters, reranked with a cross-encoder before results are returned
- **Ask mode:** ask a question in plain language and get an answer grounded in retrieved paper content, with citations to the source paper and section, and an inline relevant figure when one applies
- **Vision-aware answers:** when a retrieved figure is relevant to the question, the answer is generated by a vision-capable model that reasons over the image alongside the retrieved text, not just the caption
- **Continuously updated corpus:** new papers (and their figures) are ingested on a recurring daily schedule, not just at setup time
- **Section-aware indexing:** paper text is split by detected section (introduction, method, results, etc.) where possible, and reference lists are excluded from search
- **Expandable search & ask windows:** either panel can expand to a wider, two-pane layout (results list + detail view for search; full-width conversation for ask) for a more spacious browsing experience

## Architecture

| Layer | Technology | Role |
|---|---|---|
| Frontend | Next.js, React, Framer Motion, Tailwind | Search UI and Q&A interface, deployed on Vercel |
| Backend | FastAPI (Python) | Serves search and ask endpoints, runs reranking, deployed on Google Cloud Run |
| Database | Supabase (Postgres + pgvector) | Stores paper metadata, text chunks, and figure metadata; powers hybrid search via SQL functions |
| File storage | Supabase Storage | Stores extracted figure images (JPEG, max 800px, public bucket) |
| Text embeddings | `all-MiniLM-L6-v2` (sentence-transformers) | Turns chunk text into vectors for similarity search |
| Figure embeddings | Same `all-MiniLM-L6-v2` model, applied to title + caption text | Figures are matched via caption text embeddings rather than a separate image model — more reliable for scientific diagrams than raw image-similarity approaches, and avoids a second model's memory footprint |
| Reranking | `cross-encoder/ms-marco-MiniLM-L-6-v2` | Re-scores retrieved text candidates for precision; figures use a similarity threshold |
| LLM (text) | Groq API, `openai/gpt-oss-120b` | Generates grounded answers from retrieved context |
| LLM (vision) | Groq API, `qwen/qwen3.6-27b` | Generates answers that reason over a retrieved figure alongside the text context, with automatic fallback to the text-only model if unavailable |
| Ingestion | Python script scheduled via GitHub Actions | Fetches, cleans, chunks, embeds, and captions new papers and figures daily |
| CI/CD | Google Cloud Build, triggered on push to `main` | Automatically builds, pushes, and redeploys the backend container on every backend code change |

**How a search works:** a query is embedded and matched against stored chunks using pgvector similarity combined with SQL filters on category and date, pulling a broad candidate set. That set is reranked by a cross-encoder for precision before being returned. Related figures are matched separately via caption-embedding similarity.

**How ask works:** the same retrieval and reranking pipeline runs first. The top-ranked chunks are assembled into context for the LLM, along with the single best-matching figure if its similarity clears a threshold. If a figure is included, the request routes to the vision-capable model so it can reason over the image directly; otherwise it goes to the standard text model. The LLM returns a structured JSON answer plus the specific arXiv IDs it actually drew on, which are used to build the cited sources shown in the UI — so citations reflect what the answer actually used, not just what was retrieved.

**How ingestion works:** on a daily schedule, a script queries the arXiv API for new papers in the configured category, downloads and parses each PDF, strips the reference section, splits the remaining text into chunks by detected section, embeds those chunks, and stores everything in Supabase, skipping papers already indexed. Figure extraction runs as a separate tracked step per paper (title + caption embedded, image uploaded to Supabase Storage), so a paper's text and figures can be processed independently without duplicating either on reprocessing.

## Deployment

- **Backend**: containerized with Docker, deployed to Google Cloud Run (auto-scaling, scales to zero when idle). Environment secrets like Supabase URL & key is managed via Google Secret Manager, not plaintext environment variables.
- **Frontend**: deployed to Vercel, pointed at the Cloud Run backend via `NEXT_PUBLIC_API_URL`.
- **CORS**: locked to the production frontend origin.
- **CI/CD**: a Cloud Build trigger watches the `main` branch; any push that touches `backend/` automatically rebuilds the Docker image, pushes it to Artifact Registry, and redeploys the Cloud Run service — no manual deploy steps for routine backend changes.

## Data source and compliance

Built on the [arXiv API](https://info.arxiv.org/help/api/index.html). Ingestion respects arXiv's rate limits (roughly one request every three seconds) and identifies itself with a descriptive User-Agent. Every search result and cited source links directly to the paper's original arXiv page.

Thank you to arXiv for use of its open access interoperability.
